# Этап 1: OSINT

## Используемые источники

- **Google (google.com) и техники Google Dorking** — поисковая система общего назначения, применяемая в OSINT для выявления публично доступных материалов, связанных с целевым сервисом: упоминания доменов/поддоменов, техническая документация, следы конфигураций, ссылки на административные интерфейсы, индексируемые директории, а также потенциальные признаки утечек или ошибок публикации. Использование операторов расширенного поиска позволяет точнее находить релевантные результаты; все выводы, полученные из поисковой выдачи, рассматриваются как предположения до подтверждения на последующих этапах.
- **Shodan (shodan.io)** — специализированная поисковая система по устройствам и сетевым сервисам, доступным из сети Интернет. В рамках OSINT применяется для получения первичных сведений о публичной поверхности: обнаружение доступных сервисов, анализ баннеров, сетевых метаданных и косвенных признаков используемых технологий. Результаты Shodan используются как исходные гипотезы и требуют последующего подтверждения активными методами (этап Scanning/Testing).
- **Criminal IP (criminalip.io)** — сервис киберразведки (CTI), предоставляющий информацию о сетевых активах и связанных с ними рисках на основе наблюдаемых признаков (например, открытые порты/сервисы, технологические отпечатки, индикаторы возможных уязвимостей). В работе используется для расширения контекста по цели тестирования и для формирования списка потенциально рискованных компонентов, которые далее валидируются в рамках активного обследования и ручного тестирования.

# Этап 4: Отчет

## 4.1. Подтверждение успешности выявленных атак (Evidence)

По итогам этапов **Scanning** и **Testing** для ресурса **92.51.39.106** подтверждён ряд уязвимостей в веб-компонентах, размещённых на разных HTTP-сервисах (в т.ч. на отдельных портах). Каждая проблема была верифицирована практическими доказательствами: поведенческими признаками (изменение логики работы приложения), артефактами запросов/ответов и скриншотами интерфейса.

Ниже приведён перечень подтверждённых уязвимостей и краткое описание доказательной базы. 

### 4.1.1. SQL Injection — обход аутентификации (CWE-89)

**Суть проблемы.** В форме входа в систему на двух веб-интерфейсах приложения пользовательский ввод обрабатывается небезопасно: значения полей учётных данных попадают в SQL-запрос без корректной параметризации. Это позволяет изменить логику проверки учетной записи.

**Подтверждение.**

- Подбор специальной строки во входном поле приводит к успешной аутентификации **без знания корректного пароля**.
- Успешный вход подтверждён переходом приложения в состояние “авторизован” (отображение личного кабинета/меню пользователя, доступ к закрытым разделам и т.п.).

**Риски/влияние.** Возможен несанкционированный доступ к учётным записям, компрометация данных и выполнение действий от имени пользователя/администратора (в зависимости от того, какие роли доступны при обходе).

### 4.1.2. Cross-Site Scripting (DOM-based) (CWE-79)

**Суть проблемы.** В пользовательских формах (в том числе формах ввода текстовых данных) приложение некорректно обрабатывает ввод и/или небезопасно использует данные при формировании DOM. В результате внедрённый скриптовый фрагмент исполняется в контексте страницы.

**Подтверждение.**

- Через пользовательский ввод формируется сценарий, который исполняется в браузере при отображении страницы (факт выполнения JavaScript подтверждён тестовым безопасным индикатором).
- На втором веб-интерфейсе часть подобных точек была дополнительно обнаружена автоматизированным сканированием и затем подтверждена вручную по результатам перехода по сформированному URL-параметру.

**Риски/влияние.** Возможны кража данных сессии (при небезопасных cookie-настройках), подмена содержимого страницы, фишинг внутри доверенного домена, выполнение действий от имени пользователя.

### 4.1.3. Cross-Site Scripting (Reflected) (CWE-79)

**Суть проблемы.** В функциональности поиска пользовательский ввод отражается в выдаче без должного экранирования/кодирования, что создаёт условия для отражённого XSS.

**Подтверждение.**

- Ввод специально сформированного значения в поисковую строку приводит к появлению на странице элемента, взаимодействие с которым вызывает выполнение скрипта в браузере (демонстрация выполнена безопасным тестовым индикатором).
- Аналогичный сценарий воспроизводится на обоих веб-интерфейсах.

**Риски/влияние.** Злоумышленник может подготовить ссылку и спровоцировать пользователя открыть её (социальная инженерия), после чего выполнить сценарий в контексте доверенного ресурса.


### 4.1.4. Cross-Site Scripting (Stored/Persistent) (CWE-79)

**Суть проблемы.** В механизме комментариев (в частности, привязанном к просмотру контента) отсутствует корректная фильтрация/кодирование, в результате чего вредоносный код сохраняется на стороне приложения и исполняется при последующем просмотре страницы другими пользователями.

**Подтверждение.**

- Введённый в комментарии тестовый скриптовый индикатор сохраняется и исполняется при повторном открытии страницы.

**Риски/влияние.** Это наиболее опасная форма XSS: эксплуатация может затронуть широкую аудиторию, приводить к компрометации пользовательских сессий и к массовым атакам внутри приложения.

### 4.1.5. Path Traversal (Directory Traversal) — чтение произвольных файлов (CWE-22)

**Суть проблемы.** В одном из эндпоинтов приложение использует пользовательский параметр при формировании пути к файлу без надлежащей нормализации и проверки. Это позволяет выйти за пределы разрешённого каталога и запросить произвольный файл.

**Подтверждение.**

- Было получено содержимое системного файла, доступ к которому не должен предоставляться пользователю через веб-интерфейс.
- Находка из автоматизированного сканирования была подтверждена вручную.

**Риски/влияние.** Возможна утечка конфигураций, ключей, исходного кода и иных чувствительных данных, что облегчает дальнейшую компрометацию.

### 4.1.6. Remote OS Command Injection — выполнение команд ОС через веб-интерфейс (CWE-78)

**Суть проблемы.** Один из функциональных модулей принимает пользовательский ввод и далее использует его в контексте системной команды без безопасной изоляции аргументов. Это создаёт возможность внедрения управляющих конструкций и выполнения непредусмотренных команд на сервере.

**Подтверждение.**

- Ввод специально сформированного значения приводит к выполнению на сервере команды, результат которой возвращается в HTTP-ответе/интерфейсе.
- Факт подтверждён как автоматизированным сканированием, так и ручной валидацией.

**Риски/влияние.** Одна из наиболее критичных проблем: потенциально позволяет читать файлы, изменять конфигурацию, выполнять произвольные действия в рамках прав процесса веб-приложения и развивать атаку дальше.

## 4.2. Рекомендации по устранению выявленных уязвимостей

Ниже приведены рекомендации по исправлению проблем. Приоритет внедрения предлагается определять исходя из критичности и простоты устранения: в первую очередь закрываются уязвимости, ведущие к обходу аутентификации и удалённому выполнению команд/кода.

### 4.2.1. SQL Injection (CWE-89)

**CVSS v3.1 (по расчёту):** AV:N/AC:L/PR:N/UI:R/S:C/C:H/I:H/A:H  
**Базовая оценка:** 9.6

**Рекомендации:**
- Использовать **параметризованные запросы** (prepared statements) или безопасный ORM, исключив конкатенацию пользовательского ввода со строкой SQL.
- Внедрить **строгую валидацию** входных данных на сервере (тип, длина, формат), а также корректное экранирование как дополнительный барьер (но не как единственную защиту).
- Выделить отдельную учётную запись БД для приложения и применить принцип **минимально необходимых привилегий** (без административных прав).
- Регулярно обновлять СУБД и зависимости приложения, вести учёт уязвимостей используемых компонентов.
- В качестве компенсирующей меры использовать WAF/IDS-правила и мониторинг аномалий запросов.

### 4.2.2. Cross-Site Scripting (CWE-79)

**CVSS v3.1 (по расчёту):** AV:N/AC:L/PR:N/UI:R/S:C/C:L/I:L/A:H  
**Базовая оценка:** 8.8

**Рекомендации:**
- Применять **контекстно-зависимое кодирование вывода** (HTML/атрибуты/URL/JS-контекст) при отображении пользовательских данных.
- Исключить небезопасные способы вставки данных в DOM (например, вывод “как есть”), а также ограничить использование опасных DOM-“синков”; при необходимости применять проверенные библиотеки очистки.
- Внедрить **Content Security Policy (CSP)**, ограничивающую источники скриптов и запрещающую небезопасные конструкции.
- Укрепить настройки cookie (HttpOnly/SameSite/Secure) и не передавать чувствительные данные через URL-параметры.
- Добавить регрессионные тесты безопасности (в т.ч. автоматизированные проверки) и включить XSS-проверки в пайплайн.

### 4.2.3. Path Traversal (CWE-22)

**CVSS v3.1 (по расчёту):** AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N  
**Базовая оценка:** 5.3

**Рекомендации:**
- Применять **нормализацию (canonicalization)** пути и проверять, что итоговый путь остаётся внутри разрешённого каталога.
- Использовать подход “**идентификатор → файл**”: вместо передачи имени/пути файла извне передавать безопасный ключ (ID), который на сервере сопоставляется с конкретным разрешённым файлом.
- Валидация параметров по **белому списку** (разрешённые символы/форматы), отклонение последовательностей обхода каталогов и любых относительных переходов.
- Ограничить права процесса приложения на файловую систему (минимально необходимые), вынести чувствительные файлы за пределы доступных областей.
- Вести логирование попыток чтения файлов и реагировать на повторяющиеся аномальные запросы.

### 4.2.4. Remote OS Command Injection (CWE-78)

**CVSS v3.1 (по расчёту):** AV:N/AC:L/PR:N/UI:R/S:C/C:H/I:H/A:H  
**Базовая оценка:** 9.6

**Рекомендации:**

- По возможности **исключить вызов системной оболочки** из бизнес-логики. Использовать безопасные системные API/библиотеки, которые передают аргументы без интерпретации оболочкой.
- Если вызов команд неизбежен — применять **allowlist (белый список)** допустимых операций и строго фиксированный набор аргументов; запрещать любые “свободные строки”.
- Выполнять **валидацию** данных (тип, формат, длина), а также минимизировать поверхность ввода.
- Реализовать **принцип наименьших привилегий**: запускать приложение от непривилегированной учётной записи, ограничить доступ к критичным системным ресурсам.
- Включить аудит и мониторинг подозрительных вызовов/ошибок, добавить защитные меры на уровне контейнеризации/изоляции (где применимо).
